# Универсальный проектный дашборд

Финальный план после ревью контракта. Формулы — в [metric-catalog.md](metric-catalog.md). Схемы — в `schema/`. Приёмка установки — в [install-acceptance.md](install-acceptance.md). Как локальная модель правит конфиг — в [mapping-guide.md](mapping-guide.md).

Проверка контракта:

```bash
python3 scripts/check_contracts.py
```

## 1. Продукт v1

Одна установка — одна команда со спринтовой доской Jira. PM и PO принимают решения по двум экранам. Команда без спринтов этой версией не покрывается.

Генератор: `team.yaml` + выгрузка → снимок, которому можно верить на разборе. Продукт на много команд, планировщик и SSO начинаются после того, как один снимок защищаем.

Экраны v1:

- Спринт: качество данных и движение состава (committed / added / removed), счётчики по ролям статусов, медиана цикла и ожидания, список блокеров с причинами, загрузка всего состава включая нули, burndown только при полных SP на момент входа в спринт, таблица задач.
- Период: плашка покрытия, часы в статусе по категориям (не утилизация), статистика людей с путём классификации, список эпиков с релизом и заметкой, завершение относительно состава на старте спринта.

Тренд — бейдж к последнему слепку прошлого спринта и спарклайн дневных слепков. Дыры в днях не заполняются.

## 2. Ревью и что из него взято

Контракт смотрели с трёх сторон: операционная модель разбора, корректность конвейера, поверхность, которую реально закончить. Ниже решения, а не пересказ.

Взято в контракт.

- До экрана существуют схемы каноники, снимка, правок и manifest. Одного `team.yaml` мало: виджеты успели бы зафиксировать случайный JSON.
- Движок и золотые тесты раньше UI. Иначе форма зашитого снимка становится второй спецификацией.
- Неразобранная работа — `unknown`, не «техника». `other` только по явной метке.
- Одна арифметика рабочего времени. Окно дня обязано сходиться с `hoursPerDay`.
- Карта `status → category + role` вместо зашитых имён Closed и On-hold.
- Состав спринта — membership с `addedAt` / `removedAt`, типы задач и запрет сабтасков по умолчанию.
- Jira Cloud идентифицирует людей по `jiraAccountId`.
- Ёмкость подневная: ставка, отсутствия, праздники. Поле `capacityHours` удалено.
- Два разных `accuracy` сняты. Осталось `completionVsCommitted` к составу на старте, без цвета.
- `riskScore` снят. Блокеры — список причин.
- Часы в статусе не называются утилизацией и не красятся как цель.
- Цикл — сумма интервалов в роли `active`, не спан до закрытия. Референс считал спан и тем самым тащил очередь внутрь «цикла».
- Due: дата в зоне команды; раньше срока только если дата закрытия строго раньше due.
- Запечатка таймингов сбрасывается при смене хеша правил и при выходе из terminal.
- Слепок write-once: повторный build не переписывает байты предыдущего файла.
- v1 не тянет Confluence, мессенджер и GitLab, пока ни один экран v1 их не читает.
- Первая поставка — один процесс на localhost. Compose рядом с первым живым Jira.
- Локальная модель не вводит новую версию формулы. Смена таксономии при живом manifest останавливает build.

Не взято, сознательно.

- Полный отказ от часов в статусе. Это честная диагностика перегруза (`parallelism`) и переноса (`inherited`), если не называть её утилизацией.
- Универсальный движок правил вместо списков эпиков. Списки плюс короткий `rules[]` модель компании ещё может править; произвольные правила — нет.
- Отдельный виджет due date и кольцо статусов. Те же факты уже в блокерах, таблице и счётчиках.
- Числовой балл риска даже с расшифровкой слагаемых. Слагаемые сами и есть список.
- FTE как кадровый модуль. Хватает `allocation` от 0 до 1.

## 3. Модули

Граница модуля — что он принимает и чего не знает. Общие файлы только через схемы.

| Модуль | Путь | Вход → выход | Не знает |
| --- | --- | --- | --- |
| Конфиг | `src/dashboard/config` | YAML → `TeamConfig` | JSON Jira, HTTP, виджеты |
| Каноника | `schema/canonical.schema.json` | типы сущностей | формулы |
| Коннекторы | `src/dashboard/connectors` | raw + кусок sources → bundle | правки, слепки, KPI |
| Метрики | `src/dashboard/metrics` | bundle, config, asOf, история аргументом → результаты | файлы, сеть |
| Слепки | `src/dashboard/snapshotstore` | результаты → новый файл слепка | пересчёт формул |
| Правки | `src/dashboard/edits` | edits + результаты → view | Jira |
| Оркестратор | `src/dashboard/orchestrator` | порядок collect → metrics → snapshot → apply | — единственный, кто знает порядок |
| API | `src/dashboard/api` | `GET` view, `PUT` edits | формулы; пересчёт не внутри GET |
| Web | `web` | рисует view | арифметику |
| Фикстуры | `fixtures` | seed → raw | пакет метрик |

История для бейджа и спарклайна передаётся в метрики объектом. Функция не открывает каталог слепков сама.

`GET /api/sprint` и `GET /api/team` отдают один документ маршрута: один `asOf`, покрытие, ряд спарклайна. `GET /api/metrics/{id}` отдаёт текст формулы и параметры, не значения. Пересборку запускает CLI, не кнопка на экране.

Правки — релиз и заметка эпика. Подмены чисел в `edits.json` нет. Файл открытого снимка без сервера правки не сохраняет.

Сеть: `serve` на `127.0.0.1` пишет без токена. Другой адрес слушает только с `--token-env`. `PUT` и `POST` правок и настройки тогда требуют `Authorization: Bearer` или поле формы `token`. Чужой сайт запись не делает: `Origin` должен совпасть с `Host`, `Origin: null` и `Sec-Fetch-Site: cross-site` отклоняются, а на `127.0.0.1` заголовок `Host` остаётся петлевым. `GET` токен не требует. Значение токена в репозиторий и в YAML не входит, в том числе как часть другой строки. Процесс в образе не root.

Примеры: серверная команда со SP и cloud-команда без SP, с отпуском ставки и своим календарём.

## 5. Вехи

Каждая веха заканчивается тем, что можно открыть. Следующая не начинает новые формулы, пока золото предыдущей зелёное.

### M0. Контракт

Схемы, каталог, гид сопоставления, чеклист приёмки, `scripts/check_contracts.py`.

Выход: скрипт печатает `contracts ok`; cloud-конфиг без `jiraAccountId` не проходит; второй пример без SP валиден.

### M1. Движок

Модули config, metrics, snapshotstore, orchestrator `build`, фикстура из канонического JSON (не генератор «на глаз»).

Схема модулей — [architecture.html](architecture.html). Порядок срезов, границы импорта и золотые пары — [m1-plan.md](m1-plan.md). Релиз-ноутсы — [m1-release-notes.md](m1-release-notes.md).

Золотые случаи, каждый — пара canonical → snapshot:

- due через полночь в зоне команды;
- цикл: короткий заход, возврат в очередь, выход из terminal;
- два параллельных тикета, масштаб дня, inherited и own в одном дне;
- ромб эпиков, цикл связей, метка tech поверх проектного эпика, задача без головы → unknown;
- add на день 3 и remove на день 7;
- нет SP; SP изменилось после входа в спринт;
- build в первый день, прошедших рабочих дней 0 → темп `null`;
- второй build не меняет байты первого слепка;
- `edits.json` после build тот же;
- смена `statusMap` без приёмки останавливает build.

Выход: эти случаи зелёные, текст «Как считается» показывает параметры фикстуры.

### M2. Экран «Спринт»

Модуль web читает снимок M1. KPI открывается в список включённых и исключённых. Нет SP — нет burndown и нет нулей. Нет таймингов — плашка покрытия.

Порядок экрана, границы и локальный просмотр — [m2-plan.md](m2-plan.md).

### M3. Экран «Период» и правки

Плашка `unknown` выше кольца часов. Заметка эпика жива после второго build. У человека видны ключи и путь к голове эпика. `PUT /api/edits` пишет по схеме правок.

Порядок экрана и запись правок — [m3-plan.md](m3-plan.md).

### M4. Один процесс

`collect` для фикстуры и fileimport, `build`, `serve` на localhost. Чистый клон одной командой совпадает с золотым снимком.

Порядок команды и формат выгрузки — [m4-plan.md](m4-plan.md). Релиз-ноутсы — [m4-release-notes.md](m4-release-notes.md).

### M5. Один Jira

Либо Cloud, либо Server/Data Center — тот, к которому появится доступ. Записанный ответ API и fileimport дают один снимок. Инкремент manifest. Один контейнер, токены снаружи. Confluence, мессенджер, GitLab, вторая команда, планировщик, OIDC и отдельная база не начинаются в этой вехе.

Живой сбор — Server / Data Center, Bearer из `authEnv`. Порядок и проверка — [m5-plan.md](m5-plan.md). Релиз-ноутсы — [m5-release-notes.md](m5-release-notes.md).

### M6. Мастер настройки

Форма над тем же `team.yaml`. Поля схемы не расширяются. Версия формулы остаётся 1. Экран пишет файл и не запускает сборку. Секрет в YAML не попадает: только имя `authEnv`.

Порядок и проверка — [m6-plan.md](m6-plan.md). Релиз-ноутсы — [m6-release-notes.md](m6-release-notes.md).

### M7. Compose и токен записи

Один `compose.yaml` рядом с живой Jira. Внутри контейнера процесс слушает `0.0.0.0`, на хост порт публикуется только на `127.0.0.1`. Запись с нелокального bind требует токен из переменной. `GET` остаётся открытым. Секрет в образ и в репозиторий не копируется.

Порядок и проверка — [m7-plan.md](m7-plan.md). Релиз-ноутсы — [m7-release-notes.md](m7-release-notes.md).

## 6. Пока снимку не верят

Не делаем: портфель команд, SSO, DORA, NPS, виджет планирования по каналу, цветные цели на часы и на завершение спринта, кнопку пересборки для PM.

Мастер настройки — форма над тем же YAML. Он начат в M6, когда поля схемы перестали меняться.
