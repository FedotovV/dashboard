# Универсальный проектный дашборд

План проектирования и разработки. Референс — архитектура командного дашборда CREDIT CARD (документ от 22.09.2026): два экрана («Спринт» и «Команда»), сборка из Jira, Confluence и корпоративного мессенджера, правки менеджера, дневные слепки и тренды.

Документ фиксирует продукт, контракт конфигурации, каталог метрик и порядок разработки. Формулы и параметры — в [metric-catalog.md](metric-catalog.md). Схема входного файла — в [schema/team.schema.json](../schema/team.schema.json).

## 1. Что делаем

Дашборд для PM и PO. Остальные роли (тимлид, разработчик, delivery) смотрят те же экраны, но не задают модель.

Сейчас это **генератор одной командной установки**: на вход — файл конфигурации и выгрузки источников, на выход — собранный дашборд с историей. Тот же контракт позже становится продуктом: много команд, планировщик сбора, вход в систему.

Первая версия интерфейса работает на **моделируемых данных**. Живые Jira, Confluence, GitLab и мессенджер подключаются тем же конвейером, когда появится доступ. Формулы и экраны к этому моменту уже зафиксированы тестами на фикстурах.

### Что входит в первую версию

Экраны и метрики референса:

- спринт: предупреждения, KPI с трендом к прошлому спринту, распределение статусов, cycle time, загрузка людей, риски, типы задач, burndown, соблюдение due date, полный список задач;
- команда за период (квартал или иной отрезок): статистика по людям, проекты, разрезы проектные / технические / внепроектные, время в работе, чел-часы и утилизация, происхождение часов, срез текущего спринта, velocity, ресурсы, планирование по постам в канале;
- дневные слепки KPI и сравнение с прошлым спринтом;
- правки PM поверх собранных данных (релизы, заметки, статусы планирования) — они переживают пересборку.

### Что сознательно позже

- продуктовая аналитика конечного пользователя (NPS, воронки, retention, MAU);
- портфель многих команд в одной установке;
- SSO и роли;
- DORA-метрики GitLab как отдельные виджеты (MR lead time, частота деплоев).

GitLab в первой версии — источник ссылок в блоке «Ресурсы» и место в конфиге. Метрики поставки из GitLab не смешиваются с формулами Jira.

## 2. Как устроен референс и что из него обобщаем

Референс — статическая оболочка из двух вкладок, Python-конвейер и кэш JSON. Обновление идёт агентом через MCP: сначала сырые файлы, затем расчёт, затем слепок дня.

Это удачная модель для универсального дашборда, если убрать привязку к одной компании.

| В референсе зашито | В универсальном дашборде |
| --- | --- |
| Хост Jira, id доски и спринта | `sources.jira` |
| Состав из 9 человек и русские имена | `team.members` |
| Поле эпика `customfield_11501` | `sources.jira.fields.epicLink` |
| Метка `prod_op`, правило project > tech | `taxonomy` |
| Окно 10:00–18:00, Europe/Moscow, 8 ч | `calendar` |
| Квартал Q3 и ёмкость 3600 ч | `period` |
| Канал «Планирование банка» | `sources.messenger` + `planning` |
| Статусы Closed / Canceled, порог 15 мин в статусе | `workflow` |
| Набор блоков на двух экранах | `ui.widgets` — библиотека, состав включается конфигом |
| `user_edits.json` | тот же слой правок, ключи не зависят от имени команды |

Инварианты референса сохраняем:

- сырые выгрузки и посчитанный снимок разделены;
- правки менеджера первичны и не затираются пересборкой;
- тренды появляются только из истории слепков, а не из одиночного пересчёта текущего среза;
- закрытые задачи имеют неизменяемые тайминги, поэтому квартал можно обновлять дельтой;
- у каждой метрики есть текст «как считается».

Оболочку на iframe не переносим. В React это два маршрута одного приложения: `/sprint` и `/team`.

## 3. Форма продукта: файл конфигурации, мастер позже

Источник правды — `team.yaml` (допустим и JSON той же схемы).

Так лучше на текущем этапе, чем мастер настройки:

- локальная модель компании получает схему, каталог метрик и этот файл и правит YAML под свои поля, статусы и календарь;
- файл версионируется, сравнивается и валидируется;
- мастер, написанный до стабилизации схемы, придётся переписывать вместе с ней.

Мастер — следующая оболочка над тем же файлом, не вторая модель данных. Он нужен, когда схема перестанет меняться: человек вставляет ссылки на Jira, Confluence, доску и страницу команды, получает черновик YAML, модель или человек дописывает состав, эпики и карту статусов.

Секреты в файл не пишутся. В конфиге только имя переменной окружения (`authEnv: JIRA_TOKEN`).

## 4. Архитектура

```
team.yaml                  контракт команды
        │
        ▼
connectors/                выгрузка → cache/raw/
  fixture                  моделируемые данные (первая версия)
  fileimport               JSON/CSV, снятые вручную
  jira                     Cloud и Server/Data Center
  confluence               Cloud и Server/Data Center
  gitlab
  mattermost               первый живой мессенджер; Slack — тот же порт
        │
        ▼
canonical/                 Issue, StatusChange, Sprint, Person, Link, Post, Resource
        │
        ▼
metrics/                   чистые функции, версия каталога
        │
        ▼
snapshot/                  sprint.json, team.json, snapshots/YYYY-MM-DD.json, edits.json
        │
        ▼
api (FastAPI)              отдать снимок, сохранить правки, запустить сбор
web (React)                Спринт и Команда, тексты расчётов, RU
```

Сборка — команда, а не скрытый побочный эффект UI:

```
dashboard collect --team team.yaml    # коннекторы → cache/raw
dashboard build   --team team.yaml    # каноника → метрики → снимок + слепок дня
dashboard serve                       # API + статика UI
```

`collect` и `build` разделены. Пока нет сети до Jira, `collect` читает фикстуру или положенные в каталог файлы. `build` от источника не зависит.

### Хранение

Первая версия хранит файлы: их можно отдать модели, положить в git команды и поднять в контейнере без базы.

- `cache/raw/` — как пришло из источника;
- `cache/canonical/` — нормализованные сущности;
- `data/sprint.json`, `data/team.json` — то, что рисует UI;
- `data/snapshots/<date>.json` — дневной слепок KPI спринта и агрегаты периода;
- `data/edits.json` — правки PM;
- `data/manifest.json` — когда снято, какой sprint id, какие ключи уже имеют тайминги (для дельты).

Когда появится несколько команд и планировщик, те же JSON останутся форматом обмена. Запросами займётся SQLite в том же контейнере, без смены формул.

### Контракт API

- `GET /api/sprint`, `GET /api/team` — текущий снимок;
- `GET /api/meta` — время сборки, источник (fixture / file / live), предупреждения, версия каталога метрик;
- `GET /api/metrics/{id}` — формула, входы, параметры, текущие значения параметров;
- `PUT /api/edits` — слияние правок;
- `POST /api/rebuild` — `build` (и `collect`, если источник это умеет);
- `GET /api/health`.

UI может открыть снимок и без API: те же JSON лежат рядом со сборкой. Это сохраняет свойство референса «открыть собранный дашборд файлом».

## 5. Каноническая модель

Коннектор приводит любой источник к одним сущностям. Метрики читают только их.

- **Issue** — key, summary, type, status, statusCategory, assignee, priority, storyPoints, dueDate, resolutionDate, created, labels, components, parent/epic;
- **StatusChange** — issue, status, enteredAt, exitedAt;
- **Sprint** — id, name, state, start, end, boardId;
- **Link** — from, to, type (Child, Epic, Blocks);
- **Person** — id из конфига, отображаемое имя, имя в Jira;
- **Resource** — icon, label, value, url (Confluence и ручные ссылки из конфига);
- **ChannelPost** — id, author, createdAt, text, url (планирование).

Поля Jira Cloud и Server различаются (имена story points, epic link, формат changelog). Это различие закрывается в коннекторе, не в метрике. В фикстуре сразу есть оба профиля полей, чтобы карта `sources.jira.fields` проверялась без живого сервера.

## 6. Библиотека виджетов

Виджет объявляет, какие метрики ему нужны, и включается в `ui.widgets`. Выключенный виджет не запрашивает данные и не занимает место.

Экран **Спринт**

| Виджет | Метрики |
| --- | --- |
| Предупреждения | hygiene |
| KPI и тренд | count, done, inProgress, storyPoints, prevSprint |
| Кольцо статусов | statusMix |
| Цикл | cycleTime, dueCategory |
| Загрузка | personLoad (только состав команды) |
| Риски | blockers, riskScore |
| Типы | typeMix |
| Burndown | burndown (скрыт, если story points нет) |
| Due date | dueCategory по людям команды |
| Все задачи | список + CSV |

Экран **Команда**

| Виджет | Метрики |
| --- | --- |
| Статистика по людям | classification по исполнителю |
| Предупреждения данных | coverage, пустые эпики, неполный timing |
| Текущие проекты | эпики + правки релизов и заметок |
| Кольцо задач периода | project / tech / other |
| Время в работе | workHours по категориям |
| Внепроектные | otherSubtype prod / tech |
| Чел-часы | manhours, utilization, parallelism |
| Происхождение часов | inherited vs own |
| Спринт по категориям | те же категории на задачах спринта |
| Velocity | planned, closed, accuracy |
| Время спринта | workHours с обрезкой по датам спринта |
| Ресурсы | список ссылок |
| Планирование | посты канала + правки статуса, порядка, текста |

Story points необязательны. Нет поля в конфиге или нет значений в данных — KPI по SP и burndown не показываются. Остальные метрики считаются.

## 7. Прозрачность расчётов

Каждая метрика в каталоге имеет:

- стабильный `id` и версию;
- текст на русском: что измеряем, формула, какие задачи входят, чего метрика не измеряет;
- входы из канонической модели;
- параметры и их значения по умолчанию;
- ссылку на тест с золотым файлом.

UI показывает короткий текст всегда и полный разбор в блоке «Как это считается» — как методология чел-часов в референсе.

Менять расчёт можно двумя способами.

1. **Параметр** в `team.yaml` (`metrics.cycleTime.minStaySeconds`, календарь, карта статусов, приоритет категорий). Код формулы тот же, в «Как считается» подставляются фактические параметры этой установки.
2. **Новая версия формулы** в каталоге. Вместе с ней обновляется золотой тест и абзац в каталоге. Старая версия остаётся адресуемой, чтобы слепки прошлого периода объяснялись той формулой, которой были посчитаны.

Инструкция для локальной модели — в конце [metric-catalog.md](metric-catalog.md): что можно менять в YAML, что считается сменой формулы, какие инварианты не ломать (правки менеджера, иммутабельность таймингов закрытых задач, тренд только из слепков).

## 8. Тренды

Тренд — отдельный результат конвейера, как шаг 5 референса.

Каждый успешный `build` дописывает `snapshots/<date>.json`:

- id и границы спринта;
- KPI: всего, закрыто, в работе, SP, средний цикл, доля due date;
- размер на старте спринта (самый ранний слепок этого sprint id) и сколько задач добавили позже;
- за период: чел-часы по категориям, утилизация, покрытие классификацией.

Смена `sprint.id` закрывает предыдущий слепок в `prev` и начинает новый ряд. Так бейдж «к прошлому спринту» не сравнивает разные спринты по ошибке.

На экране:

- бейдж KPI против прошлого спринта;
- спарклайн по дневным слепкам текущего спринта;
- на командном экране — ряд периодов, когда их в снимках больше одного (сначала один квартал фикстуры и «прошлый» период, чтобы ряд был виден сразу).

Пока сбор ручной, пропущенные дни остаются пропусками. Линия их не интерполирует.

## 9. Сбор данных

### Сейчас

- **fixture** — согласованный генератор: два спринта, состав, эпики обеих категорий, changelog со статусами, страница ресурсов, посты планирования, дыры в данных (нет исполнителя, нет срока, нет SP, просрочка, задача в работе с прошлого периода). Зерно фиксировано, тесты стабильны.
- **fileimport** — каталог с JSON в форме каноники или сырого Jira. Скрипт человек запускает сам. Этот режим и есть «ручной сбор» до появления сети.

Оба режима пишут один и тот же `cache/raw`, дальше работает один `build`.

### Потом, без смены метрик

- Jira Cloud (`/rest/api/3`, API token) и Jira Server/Data Center (`/rest/api/2`, PAT);
- Confluence в тех же двух вариантах;
- Mattermost как открытый аналог Slack: посты канала планирования. Slack подключается тем же интерфейсом `ChannelPosts`;
- GitLab: проекты и ссылки, затем отдельный пакет виджетов поставки.

Запросы к живому источнику идут последовательно, с паузой и повтором на 429 — как в референсе. Инкремент квартала: manifest помнит `updated` и ключи с уже снятыми таймингами; закрытые задачи повторно не обходятся.

В первой версии интерфейс инкремента есть у fileimport и fixture (повторный collect меняет только «открытые» задачи). Живой Jira его реализует позже на том же manifest.

## 10. Интерфейс

React и Vite. Два маршрута, общий каркас: название команды из конфига, время сборки, переключатель Спринт / Команда, ссылка на предупреждения данных.

Язык интерфейса — русский. Английский остаётся у имён систем, полей API, статусов Jira as-is и идентификаторов метрик. Строки UI лежат в словаре, чтобы позже добавить полный EN без переписывания экранов.

Визуальный язык референса: плотные карточки, кольца, мини-бары загрузки, таблица задач, жёлтые плашки о дырах в данных. Кольца и бары — свои SVG-компоненты, чтобы подпись единиц («зад.», «чел-ч») была частью виджета. Линия burndown и спарклайн — один небольшой графический компонент.

Правки PM доступны на командном экране и сохраняются через API в `edits.json`. В режиме открытого файла правки держатся в браузере и помечаются как локальные, пока нет сервера.

Пустые состояния обязательны: нет SP, нет таймингов, классификация не покрыла задачи, канал планирования пуст. Текст плашки говорит, какого шага сбора не хватает.

## 11. Поставка

Один `docker-compose` для ноутбука и для сервера:

- сервис `web` отдаёт собранный React;
- сервис `api` на Python запускает collect/build и раздаёт снимок;
- том `./data` — конфиг, кэш, снимки, правки.

Профиль `fixture` поднимается без секретов и показывает дашборд сразу. Профиль `live` читает токены из окружения и включает коннекторы. Облако — тот же compose за обратным прокси. Отдельного облачного кода в первой версии нет.

Аутентификация в первую версию не входит: установка считается локальной или сетево закрытой. В API заранее есть место для проверки запроса, чтобы позже повесить OIDC, не переписывая снимки и правки. Роли откладываем: сначала один редактор правок, остальные смотрят.

## 12. Порядок разработки

Каждая фаза заканчивается тем, что можно открыть и проверить. Следующая фаза не начинает новые формулы, пока золотые тесты предыдущей зелёные.

### Фаза 0. Контракт

Уже начата этим документом.

- схема `team.yaml`;
- каталог метрик с формулами референса и параметрами;
- описание канонических сущностей;
- список виджетов и какой метрике какой виджет соответствует.

Готово, когда по схеме валидируются пример команды и пример с другими статусами, календарём и без story points.

### Фаза 1. Интерфейс на фикстуре

- каркас двух экранов;
- все виджеты из раздела 6 на зашитом снимке;
- блоки «Как это считается» из каталога;
- плашки неполных данных;
- правки PM в локальном состоянии;
- русский словарь строк.

Готово, когда по фикстуре видны оба экрана, тренд к прошлому спринту, пустой burndown при отсутствии SP и раскрытие задач человека по категориям.

### Фаза 2. Движок метрик

- пакет чистых функций на Python;
- `build` из канонического JSON в `sprint.json` и `team.json`;
- слепок дня, `prev`, спарклайн;
- золотые тесты на формулы раздела F референса: cycle time, due date, risk score, классификация project > tech, сжатие дня до 8 часов, утилизация, inherited/own.

Готово, когда смена календаря или порога минут в статусе меняет числа и текст «Как считается», а файлы правок после `build` те же.

### Фаза 3. Сбор скриптом и контейнер

- генератор фикстуры с фиксированным зерном;
- fileimport;
- команды `collect`, `build`, `serve`;
- `PUT /api/edits` и пересборка;
- docker-compose профиль `fixture`.

Готово, когда чистый клон поднимается одной командой и показывает тот же снимок, что золотой тест.

### Фаза 4. Живые источники

- Jira Cloud и Server/Data Center;
- Confluence Cloud и Server;
- Mattermost;
- GitLab как ресурсы;
- инкремент по manifest;
- профиль compose `live`.

Готово, когда одна и та же команда `build` считает снимок и из фикстуры, и из выгрузки живого Jira, положенной в fileimport (сверка на сохранённом ответе API, без обязательного доступа из CI).

### Фаза 5. Задел под продукт

- каталог нескольких `team.yaml` в одной установке;
- планировщик collect/build;
- OIDC на уже готовой точке проверки запроса;
- виджеты GitLab отдельно от экранов спринта и команды;
- SQLite как индекс слепков, JSON остаётся выгрузкой.

## 13. Принятые решения

Их можно поменять, на план фаз 0–3 это не влияет.

- Одна установка в первой версии — одна команда. Портфель — фаза 5.
- Мессенджер в коде — порт постов канала. Первый боевой адаптер — Mattermost. Slack использует тот же порт.
- GitLab не участвует в формулах спринта и квартала.
- «Метрики продукта» в первой версии — это разрезы проектной и продуктовой работы из референса (категории, внепроектные с подтипом, планирование), а не аналитика поведения пользователей.
- Мастер настройки — после стабилизации схемы. До него настройка — YAML и валидация схемой.
- Аутентификацию и роли выбираем отдельно, до фазы 5.
- Story points, названия статусов, поле эпика, состав и календарь всегда приходят из конфига. В коде остаются только формулы и значения по умолчанию каталога.

## 14. Как локальная модель адаптирует дашборд

Модели отдают три файла: `schema/team.schema.json`, `docs/metric-catalog.md`, текущий `team.yaml`.

Модель меняет конфиг под компанию: адреса, карту полей, статусы, состав, эпики, подписи виджетов, параметры метрик. Модель не переписывает формулы в коде. Если компании нужна другая формула, она добавляет версию в каталог и тест, а в YAML указывает `metrics.<id>.version`.

Проверка адаптации: схема проходит валидацию, `build` на фикстуре или fileimport этой компании завершается, предупреждения покрытия классификацией прочитаны, тексты «Как считается» показывают уже новые параметры.
