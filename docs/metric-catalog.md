# Каталог метрик

Версия каталога: `1`.

Все установки считают метрики этими формулами. Отличаются параметры в `team.yaml`: календарь, статусы, таксономия, пороги. Текст «Как это считается» в интерфейсе собирается из этого файла и фактических параметров установки.

Обозначения:

- рабочий интервал — пересечение отрезка времени с окном `calendar.workStart`–`calendar.workEnd` в `calendar.timezone` по дням `calendar.workdays`;
- `hoursPerDay` — из календаря, по умолчанию 8;
- категория задачи — `project`, `tech`, `other`, `unknown`;
- подтип `other` — `prod` или `tech`.

Если в конфигурации задан `metrics.<id>.version`, считается указанная версия. Пока в каталоге одна версия у каждой метрики.

## cycleTime

Версия `1`. Экран: Спринт, блок «Метрики цикла».

Что измеряет: сколько рабочих дней задача была в рабочем статусе до завершения.

```
cycleDays = work_days(inProgressAt, resolutionDate или terminalAt)
work_days(t0, t1) = round(секунды рабочего интервала / hoursPerDay, 2)
```

- `inProgressAt` — первый вход в рабочий статус, если пребывание в нём не короче `metrics.cycleTime.minStaySeconds` (по умолчанию 900). Более короткие заходы считаются автопереходом и пропускаются.
- Рабочий статус — любой, кроме `workflow.nonWorkingStatuses`.
- `terminalAt` — первый вход в `workflow.terminalStatuses`.
- В среднее и медиану входят только задачи категории статуса Done с посчитанным `cycleDays`.
- Нет таймингов — виджет показывает плашку, числа не подменяются нулём.

Параметры: `minStaySeconds`, календарь.

Не измеряет: календарные сутки, время в очереди до первого рабочего статуса, трудозатраты по списанию.

## dueCategory

Версия `1`. Экран: Спринт, сводка и таблица по людям.

Только задачи Done.

```
нет dueDate                         → без срока
дата resolution ≤ дата due          → ранее срока
даты равны                          → в срок
иначе                               → позже срока
```

Сравнение по календарным датам, без времени. В таблицу по людям попадает исполнитель из `team.members`. Сводка по рискам и полная таблица задач фильтр состава не применяют.

## sprintCounts

Версия `1`. Карточки KPI.

```
всего     = число задач спринта
закрыто   = statusCategory Done
в работе  = statusCategory In Progress
к выполнению = остальные
storyPoints = сумма SP, если поле задано и значения есть
accuracy  = Done / закрытые с resolution   # доля именно Done среди закрытых
```

Нет story points — карточка SP скрыта.

## prevSprint

Версия `1`. Бейджи на KPI.

Берётся последний слепок предыдущего `sprint.id`, а не пересчёт «вчера» текущего. Смена спринта фиксируется в `build`: новый id архивирует текущий ряд в `prev`.

Одиночный пересчёт без истории бейдж не рисует.

## hygiene

Версия `1`. Жёлтые и красные плашки.

Задача попадает в плашку, если:

- нет story points при включённом поле SP;
- нет исполнителя;
- нет due date;
- due date раньше дня сборки и статус не Done;
- приоритет из `metrics.hygiene.highPriorities` (по умолчанию Critical, High, Major) и категория To Do;
- нет исполнителя и статус не In Progress;
- возраст от `created` больше `metrics.hygiene.maxAgeDays` (по умолчанию 90).

## blockers

Версия `1`. Таблица рисков, без фильтра состава.

```
On-hold
или dueDate < день сборки и не Done
или нет исполнителя и In Progress
```

Сортировка по `riskScore` по убыванию.

## riskScore

Версия `1`.

```
просрочка × 10
+ приоритет: Critical 40, Major 25, High 20, иначе 0
+ storyPoints × 2
+ On-hold × 30
+ min(30, дни в работе / 2)
```

Дни в работе считаются от `inProgressAt`. Порог простоя:

```
idleThreshold = max(metrics.risk.idleMinDays, round(длина спринта в днях / 3))
```

`idleMinDays` по умолчанию 3.

В блок решений попадают не больше трёх задач: On-hold или просроченные с приоритетом Critical/Major или SP не ниже `metrics.risk.decisionMinPoints` (по умолчанию 5).

## forecast

Версия `1`. Текст в предупреждениях спринта.

```
rate = закрыто / прошедших дней спринта
```

Остаток делится на три корзины:

- `carry` — создано раньше `sprint.start`;
- `unplanned` — метка из `metrics.forecast.unplannedLabel` (по умолчанию `unplanned`);
- `fresh` — остальные.

```
rateK = закрыто в корзине K / прошедших дней
прогноз lo = сумма (остаток K / rateK) по корзинам, где rateK > 0
прогноз hi = остаток / rate
```

База плана — размер самого раннего слепка этого спринта (`plannedAtStart`). Добавлено в спринт = всего сейчас − `plannedAtStart`. Вердикт «план достижим» — нижняя оценка по корзине carry покрывает `plannedAtStart`.

Нет слепка старта — вердикт не показывается, есть только текущие счётчики.

## statusMix

Версия `1`. Кольцо статусов.

Доли Done / In Progress / To Do по `statusCategory`. В центре — процент закрытого от всех задач спринта.

## typeMix

Версия `1`. Распределение по `issue.type` как пришло из источника. Имена типов не переводятся.

## burndown

Версия `1`. Скрыт без story points.

Идеальная линия — равномерное сгорание суммы SP от `sprint.start` до `sprint.end`. Факт — накопленное SP задач Done по `resolutionDate`. Ось обрезается днём сборки, будущие дни факта не рисуются.

## personLoad

Версия `1`. Бары и таблица загрузки.

В расчёт входят задачи, чей исполнитель есть в `team.members` на дату сборки (`activeFrom` / `activeTo`). Для каждого: всего, в работе, к выполнению, готово. Человек состава с нулём задач в этот виджет не выводится; он остаётся в статистике периода, если там есть его задачи.

## classification

Версия `1`. Основа командного экрана.

Дерево строится вниз от эпиков `taxonomy.epics.project` и `taxonomy.epics.tech` по связям `taxonomy.linkTypes` и полю эпика.

```
категория = категория корня дерева, если задача в дереве
иначе категория ближайшего достижимого головы вверх по связям
иначе other, если задача команды и голова не найдена
иначе unknown
```

Если задача достижима из обеих веток, побеждает более ранний элемент `taxonomy.priority` (по умолчанию project, затем tech).

Режим `taxonomy.techMode`:

- `epics` — технические корни из списка эпиков;
- `label` — техническая задача по метке `taxonomy.techLabel`;
- `project` — техническая задача по проекту Jira `taxonomy.techProjectKey`;
- `none` — ветки tech нет, всё вне project становится other.

Задача команды: исполнитель в `team.members` или в alumni, и дата попадает в его окно. Одного компонента Jira недостаточно.

Подтип other:

```
есть метка taxonomy.otherSubtype.prodLabel (по умолчанию prod_op) → prod
иначе → tech
```

Покрытие:

```
unknownPct = unknown / все задачи команды периода
otherPct   = other / все задачи команды периода
```

Высокий `unknownPct` (порог `metrics.classification.unknownWarnPct`, по умолчанию 15) даёт плашку: не хватает дерева эпиков или шага выгрузки связей.

## workHours

Версия `1`. Кольца «время в работе» за период и за спринт.

```
work_hours(t0, t1) = floor(секунды рабочего интервала / 3600)
```

Для периода интервал обрезается `[period.start, момент сборки]`. Если у верхней границы известна только дата, берётся конец рабочего дня. Для спринта обрезка `[sprint.start, sprint.end, момент сборки]`.

Источник таймингов периода:

- `full` — тайминги есть по задачам периода;
- `partial` — только тайминги текущего спринта, кольцо помечается как неполное;
- `none` — кольцо в пустом состоянии.

Это часы пребывания в рабочем статусе, не списанные трудозатраты.

## manhours

Версия `1`. Чел-часы, параллельность, утилизация.

```
day_load[дата][человек][категория] = сумма work_hours его задач в этой категории за день
```

Если сумма категорий человека за день больше `hoursPerDay`, все категории этого дня умножаются на `hoursPerDay / сумма`. Доли категорий сохраняются.

```
manhoursTotal  = сумма нормированного day_load
parallelism    = часы до нормировки / manhoursTotal
capacity       = hoursPerDay × прошедшие рабочие дни периода × число людей состава
                 или period.capacityHours × прошедшие рабочие дни / рабочие дни периода
utilization    = manhoursTotal / capacity × 100%
```

Ёмкость — прошедшая, не весь квартал вперёд. Выработка выше 100% возможна, если в составе меньше людей, чем фактических исполнителей, или календарь не совпал с фактом; плашка объясняет формулу, число не обрезается.

Нет таймингов — ряд скрыт.

## hourOrigin

Версия `1`.

```
inheritedHours = нормированные часы задач, у которых inProgressAt раньше period.start
ownHours       = manhoursTotal − inheritedHours
```

Задача, уже бывшая в работе на границе периода, не считается начатой в периоде.

## velocity

Версия `1`. Бары спринта на командном экране.

```
planned  = число задач в срезе спринта (знаменатель бара = 100%)
closed   = Done
accuracy = closed / planned
```

Цвет аккуратности задаётся порогами `metrics.velocity.thresholds`: ниже `low` (50) — внимание, от `low` до `high` (80) — промежуточно, выше `high` — в плане. Пороги команда меняет в YAML.

Это отношение закрытых к лежащим в спринте сейчас, а не к `plannedAtStart`. Второе число живёт в `forecast` и в слепках.

## personPeriodStats

Версия `1`. Таблица «команда за период».

По каждому человеку состава: число задач project / tech / other / unknown и список ключей. Задачи без `resolutionDate` показываются отдельно («+n»), в закрытые не входят. Раскрытие other делит список на prod и tech.

## projectList

Версия `1`. Таблица эпиков.

Строка — головной эпик из таксономии: тип ветки, название, статус, due date, feature lead из конфига. Релиз и заметка читаются из `edits.json` (`projectReleases`, `projectNotes`) и при пересборке подставляются поверх среза.

Пустой список эпиков в конфиге даёт плашку, а не пустую таблицу без объяснения.

## resources

Версия `1`.

Базовые строки из конфига: канал, как завести задачу, компонент, доска, PM, тимлид, страница команды. Дополнительные — из выгрузки страницы Confluence. Совпадение по подписи или имени пользователя: остаётся строка из конфига.

## planningBoard

Версия `1`.

Строка — ожидаемый пост из `planning.targets` плюс найденные посты канала. Поля с правками: статус, текст проектов, порядок строк, флаг «планирование скрыто». Срок подсвечивается по `metrics.planning.urgentDays` (3) и `soonDays` (5).

Нет выгрузки канала — строки целей остаются, в колонке поста «нет поста».

## Что модели можно менять без новой версии формулы

В `team.yaml`:

- `calendar` — пояс, окно, рабочие дни, часов в дне;
- `workflow.nonWorkingStatuses`, `terminalStatuses`;
- `metrics.cycleTime.minStaySeconds`;
- `metrics.hygiene.highPriorities`, `maxAgeDays`;
- `metrics.risk.idleMinDays`, `decisionMinPoints`;
- `metrics.forecast.unplannedLabel`;
- `metrics.velocity.thresholds`;
- `metrics.classification.unknownWarnPct`;
- `metrics.planning.urgentDays`, `soonDays`;
- `taxonomy` — эпики, приоритет веток, режим tech, метка подтипа, типы связей;
- `team.members` и окна активности;
- `period` и при необходимости `capacityHours`;
- `sources.jira.fields` — story points, epic link и другие id полей;
- `ui.widgets` — какие блоки включены.

После правки YAML пересобирают снимок. Текст «Как считается» должен показать новые параметры. Золотой тест с дефолтами при этом не меняется: для своих параметров команда хранит свой ожидаемый снимок.

## Что считается новой версией формулы

Другое определение cycle time, другая нормировка дня, другой приоритет project/tech, включение календарных выходных в часы, замена accuracy на другое отношение.

Тогда:

1. в каталог добавляется версия `2` с полным текстом, версия `1` остаётся;
2. в пакет метрик добавляется функция этой версии;
3. золотой тест фиксирует обе версии на одной фикстуре;
4. в YAML команды ставится `metrics.<id>.version: 2`;
5. слепки, посчитанные версией `1`, хранят номер версии в `manifest`, чтобы история не переобъяснялась новой формулой.

Не менять при адаптации:

- правки в `edits.json` переживают любой `build`;
- тайминги задачи в терминальном статусе не пересчитываются заново, если ключ уже в manifest;
- `prev` и спарклайн пишутся только из слепков;
- виджеты не считают формулы сами — они рисуют поля снимка.
