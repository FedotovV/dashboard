# Каталог метрик

Версия каталога: `1`.

Движок считает только эти формулы. Текст «Как считается» берётся отсюда и из фактических параметров `team.yaml`. Неизвестная `metrics.<id>.version` останавливает `build`. Новую версию формулы добавляет человек вместе с золотым тестом; локальная модель этого не делает.

Число в снимке — объект `{id, version, unit, value|null, population, excluded, warnings, params}`. `null` не заменяется нулём.

## Время

Все инстанты хранятся в UTC. Календарная дата режется только в `calendar.timezone`. Имя слепка и «сегодня» — дата в этой зоне, не в зоне машины.

Рабочий день — день из `workdays` или `extraWorkdays`, и не из `holidays`. Окно `[workStart, workEnd)` минус `breakMinutes`. Инвариант конфига: длина окна минус перерыв равна `hoursPerDay`. Иначе `build` отклоняет файл.

```
nominalSeconds = hoursPerDay × 3600
workSeconds(t0, t1) = секунды пересечения [t0, t1) с рабочими окнами
```

Один квант на все метрики: секунды, без `floor` по часам в одной формуле и `round` по дням в другой. В карточке дни показывают как `workSeconds / nominalSeconds`, округление только в подписи (2 знака).

Интервалы полуоткрытые. Верхняя граница, заданная датой, — `workEnd` этой даты. Если прошедших рабочих дней 0, метрики темпа равны `null`.

Роль статуса берётся из `workflow.statusMap`, не из названия в коде.

## cycleTime

Версия `1`. Медиана времени в роли `active`.

Это не спан от первого входа до закрытия. Возврат в очередь между двумя заходами в работу в медиану не входит. Референс считал спан; для решения PM это смешивает ожидание с работой, поэтому v1 от референса отходит. Ожидание — отдельная метрика `waitTime`.

```
отрезки = интервалы statusChanges, где role = active и длительность ≥ minStaySeconds
cycleSeconds = сумма workSeconds по отрезкам до первого входа в terminal
value = медиана cycleSeconds / nominalSeconds по задачам category done
```

Короче `minStaySeconds` (по умолчанию 900) — автопереход, в сумму не входит, ключ попадает в `excluded` с причиной `shorter-than-min-stay`.

Нет ни одного `statusChanges` — задача в `excluded` (`no-timing`), метрика `null`, если таких большинство (`coverage.timing = none`).

`waitTime` считается так же по роли `wait`. Обе цифры живут в одной карточке KPI. Цель на них не ставят.

Выход из `terminal` снимает запечатку в manifest, цикл считается заново.

## sprintFlow

Версия `1`. Счётчики текущего состава спринта.

В состав входят задачи, у которых `membership.removedAt` пуст, `type` в `scope.issueTypes`, `projectKey` в `scope.projectKeys` (если список задан), и `subtask = false`, когда `countSubtasks = false`.

```
всего     = этот состав
active    = role active
wait      = role wait
hold      = role hold
queue     = role queue
done      = role terminal и outcome completed (поле пустое = completed)
canceled  = role terminal и outcome canceled
```

Отменённая задача остаётся в знаменателе `completionVsCommitted` и не попадает в числитель. Снятие её из знаменателя улучшало бы процент за счёт отмен. Доля «Done среди всех закрытых» не считается. В таблице виден исходный статус.

## scopeChange

Версия `1`.

```
committed = membership.addedAt ≤ sprint.start (начало дня в TZ команды) и задача всё ещё в составе
added     = addedAt > sprint.start и removedAt пуст
removed   = removedAt задан
```

Если у задачи нет `addedAt`, `coverage.membership = incomplete`, все три числа `null`. Вычитать «всего минус старт» нельзя: снятые ключи маскируют новые.

`prevSprint` сравнивает `sprintFlow` с последним слепком предыдущего `sprint.id`. Без слепка бейджа нет. Пропуски дней не интерполируются.

## completionVsCommitted

Версия `1`.

```
value = done среди committed / committed
```

`committed` включает отменённые. Они не входят в числитель. Знаменатель — состав на старте, не «сколько задач лежит сейчас». Цветовых порогов нет. Рядом на карточке показываются `added` и `removed` из `scopeChange`.

Прогноз «успеем ли» в v1 нет: темп первых дней шумит, а сравнение дней и штук в референсе было ошибкой единиц.

## hygiene

Версия `1`. Плашки качества данных, не рейтинг команды.

Задача попадает в плашку по одной причине:

- нет story points, если поле SP задано и значение пусто;
- нет исполнителя и роль `active`;
- нет due date, если `usesDueDate` и роль ещё не `terminal`;
- приоритет из `highPriorities` и роль `queue`;
- возраст от `created` больше `maxAgeDays` и роль не `terminal`.

Пустой исполнитель не дублируется второй плашкой. Просроченный due — не гигиена, а причина блокера.

## blockers

Версия `1`. Список, не балл.

Причина ставится, если:

- роль `hold`;
- `usesDueDate`, due date раньше сегодня в TZ команды, роль не `terminal`;
- нет исполнителя и роль `active`.

Сортировка: просроченное обязательство, затем hold, затем пустой исполнитель. Числового `riskScore` нет: вес SP поднимал крупную историю выше просроченного блокирующего дефекта.

## personLoad

Версия `1`.

Все люди из `members`, у кого `asOf` внутри `[activeFrom, activeTo]` и не внутри `absences`. Человек с нулём открытых задач остаётся в списке. Открытая задача — роль не `terminal` и задача в текущем составе спринта.

## burndown

Версия `1`. Считается только при `coverage.storyPoints = full`: поле SP задано и у каждой задачи состава есть `storyPointsAtAdd`.

Идеальная линия — равномерное сгорание суммы `storyPointsAtAdd` от `sprint.start` до `sprint.end`. Факт — накопленное SP задач, перешедших в `terminal`, по дате этого перехода. Текущая оценка, изменённая после старта, линию не двигает. Иначе `value = null` и виджет скрыт.

## classification

Версия `1`.

Рёбра — `taxonomy.linkTypes` и поле epic link. Направление: `fromId` родитель, `toId` потомок. `Blocks` ребром быть не может. Обход вниз от `taxonomy.epics`, множество посещённых, циклы обрываются. Ничья двух голов одной глубины: раньше в `taxonomy.priority`, затем меньший id родителя.

```
есть голова дерева            → категория этой головы
иначе совпало taxonomy.rules → категория правила, первое по порядку
иначе есть prodLabel         → other / prod
иначе есть techLabel         → other / tech
иначе                         → unknown
```

Задача без головы не становится «технической». `other` существует только по явной метке. `unknownPct` выше `unknownWarnPct` (по умолчанию 15) поднимает плашку над кольцом часов.

В состав человека за период входят его задачи с `created` или активностью внутри периода; дата активности — `enteredAt` первого `active`. Окна `activeFrom` / `activeTo` и отсутствия режут и список, и ёмкость.

## statusHours

Версия `1`. Подпись на экране: «часы в статусе, не списание». Это не утилизация и не цель.

```
сырые секунды человека за день = сумма workSeconds его задач с role active
если сумма > nominalSeconds × allocation — категории дня умножаются на этот предел / сумму
```

Масштаб применяется после разложения по задачам, затем категории суммируются. Так доля inherited не зависит от порядка округления.

```
inherited = секунды этого периода у задач, чей первый active раньше period.start
own       = scaled − inherited
capacity  = сумма по прошедшим рабочим дням (nominalSeconds × allocation) людей, активных в этот день и не в отсутствии
statusTimeRatio = scaled / capacity
parallelism = raw / scaled
```

`statusTimeRatio` показывается как диагностика рядом с `parallelism`. Цвета «норма / плохо» нет. Выше 100% возможно, если в часы попали исполнители вне состава: они видны отдельной строкой «вне состава» и в ёмкость не входят.

Нет таймингов — ряд скрыт, `coverage.timing` объясняет почему.

## projectList

Версия `1`. Строка — эпик из `taxonomy.epics`: ключ, имя, статус, feature lead. Релиз и заметка подставляются из `edits.json` по `epicId`. Чужой id в правках даёт warning и не исчезает молча. Пустой список эпиков — плашка, не пустая таблица.

## coverage

Не виджет. Поля снимка: `timing` (`full|partial|none`), `unknownPct`, `storyPoints` (`off|partial|full`), `assigneeMatchPct`, `membership` (`complete|incomplete`). UI прячет кольцо и burndown, когда покрытие этого не позволяет.

## Что считает drill-down

По каждой метрике v1 в снимке уже лежат `population` и `excluded` с причиной. Для классификации в снимке периода нужен путь: ключ → id головы или причина `unknown`. Для `statusHours` — секунды человека за один выбранный день до масштаба и после. Отдельного числового разложения риска нет.

## Не входит в v1

Остаются в референсе и не переносятся, пока снимку v1 не доверяют:

- кольцо статусов (те же числа, что `sprintFlow`);
- распределение типов задач;
- отдельная таблица due date (просрок — причина блокера, колонка due есть в списке задач);
- цветовая accuracy и пороги 50/80;
- вердикт «план достижим»;
- второе кольцо спринта на экране периода;
- ресурсы Confluence и посты канала;
- карточный KPI «утилизация».

## Что модель может менять в YAML

Календарь, `statusMap`, состав, отсутствия, `allocation`, эпики, `rules`, метки other, `scope`, `usesDueDate`, `minStaySeconds`, `unknownWarnPct`, `highPriorities`, `maxAgeDays`, поле SP (`null` выключает burndown).

После правки нужен новый `build`. Если хеш `calendar`, `workflow`, `taxonomy` или `scope` разошёлся с manifest, `build` останавливается, пока человек не примет пересчёт. Запечатанные тайминги при смене карты статусов не сохраняются.

Модель не добавляет версию формулы, не пишет веса риска и не кладёт пороги цвета.
