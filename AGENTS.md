# Agent instructions

### Overview & Scope

Репозиторий — контракт универсального командного дашборда для PM и PO. Кода приложения нет: только план, каталог метрик и схема `team.yaml`. Этот файл действует на весь репозиторий. Вложенных `AGENTS.md` нет; если появятся, ближайший к файлу побеждает.

Источник правды: `docs/plan.md`, `docs/metric-catalog.md`, `schema/team.schema.json`. README только указывает на них.

### Agent Role

Агент — инженер, который реализует план, не расширяя продукт.

Можно: править контракт, когда пользователь меняет решение; начинать фазы из `docs/plan.md` по порядку; добавлять параметры метрик в схему и каталог вместе.

Нельзя: вводить метрики, экраны и источники, которых нет в плане; менять смысл формулы без новой версии в каталоге; писать секреты в YAML; переносить в код хосты, id досок и имена людей из внутреннего референса.

### Build, Test & Validation Commands

Установки, сборки, линтера и тестов в репозитории нет. Не выдумывать `npm`, `pytest`, Docker-команды, пока соответствующих файлов нет.

Единственная проверка, она проходит при установленных PyYAML и `jsonschema` (в репозитории зависимости не зафиксированы):

```bash
python3 -c 'import json,yaml; from jsonschema import Draft202012Validator; s=json.load(open("schema/team.schema.json")); d=yaml.safe_load(open("schema/examples/team.example.yaml")); Draft202012Validator.check_schema(s); e=list(Draft202012Validator(s).iter_errors(d)); assert not e, e'
```

Даты в примере YAML держать в кавычках: PyYAML иначе превращает их в `date`, и схема отклоняет файл.

### Conventions & Patterns

- Документы и подписи продукта — на русском. Английский — у имён систем, полей API, статусов Jira as-is и `id` метрик.
- Конфиг команды — `team.yaml` по `schema/team.schema.json`. Пример: `schema/examples/team.example.yaml`.
- Формула живёт в `docs/metric-catalog.md`. Виджет рисует поля снимка и не считает метрику сам.
- Параметр (календарь, статусы, пороги) меняется в YAML. Другая формула — версия `2` в каталоге, старая версия остаётся.
- Story points необязательны: `sources.jira.fields.storyPoints: null` скрывает SP и burndown.
- Jira Cloud и Server/Data Center различаются в коннекторе, не в метрике.
- Сбор (`collect`) и расчёт (`build`) разделены. Тренд пишется только из `snapshots/`. Правки PM лежат в `edits.json` и переживают пересборку.
- Планируемый стек, когда появится код: React (Vite) и Python (FastAPI). Каталоги из плана: `web`, `api`, `metrics`, `connectors`. До кода эти каталоги не создавать заранее.
- Искать по `docs/` и `schema/`. Игнорировать `.git/`.

### Dos and Don’ts

- Сверять числа и виджеты с каталогом, а не с памятью о референсе.
- Обновлять пример YAML и прогонять проверку схемы в том же изменении, что и схему.
- Писать в «Как считается» фактические параметры установки.
- Не добавлять NPS, воронки, DORA, мультикомандность и SSO раньше фазы, где они указаны, и без явной просьбы.
- Не зашивать календарь 10:00–18:00, `Europe/Moscow`, метку `prod_op` и правило project > tech в код как единственный вариант: это значения по умолчанию каталога.
- Не дублировать план в README.

### Safety & Guardrails

- Секреты только через `authEnv` и окружение.
- Не подключаться к чужим Jira, Confluence, GitLab и мессенджерам и не класть в репозиторий выгрузки с персональными данными.
- Безопасно автоматизировать: правки схемы, каталога, плана и, после появления кода, фикстуры с фиксированным зерном.
- Не переписывать каталог формул «для ясности», если пользователь просил другую задачу.

### Git & PR Rules

- Базовая ветка: `Flutter`.
- Коммиты — законченная мысль в повелительном наклонении: что изменилось и зачем.
- В описании PR указывать, какой документ контракта изменился и прошла ли проверка схемы.
- Пока нет тестов приложения, для изменений схемы обязательна команда из раздела проверки.

### Additional rules

- Держать файл коротким. Команды и каталоги дописывать сюда, когда они реально появляются в репозитории.
- Продуктовые решения, которые можно оспорить, лежат в `docs/plan.md`, раздел «Принятые решения».
